후속 전체 검사: [남은 실패·건너뜀 검증](REMAINING-TESTS-QA.md)에서 아래에 기록된 실패 1개의 오래된 기대값을 명세에 맞게 수정하고, 감사 2개의 실행 조건을 충족했다. 최종 75파일 1,253개 통과·실패0·건너뜀0. 제품 코드는 추가 변경하지 않았고 빌드 번들은 이 성능 검증의 최종 번들과 동일하다. 아래 수치는 당시 결과로 보존한다.

기준 소스: `0c533cad7cc0bed45720135bfa5f6eed556310ab` (1.3.5). 실제 사용자 보관함은 변경하지 않았고, 원격 게시·설치·배포 패키징은 하지 않았다. 테스트 데이터·측정 플러그인은 소스 저장소 밖 `../performance-qa-2026-10-27/`에만 있다.

## 환경과 방법

- Apple M3 MacBook Air, 메모리 16GB, macOS 27.2 (26B123), Obsidian 데스크톱 1.14.5. Electron/Chromium/Node 상세 버전과 창 크기는 원시 JSON의 environment 참조.
- 별도 `MIA-Performance-QA` 보관함. 동일 앱·창·테마·데이터·측정 코드로 전후 각각 3규모 × 5회 = 15회, 16개 동작 = 240개 표본씩 수집.
- 매회 이전 화면 닫기·플러그인 비활성화→해당 규모 원본 학습 데이터와 정상 이어하기 초기값 복원→재활성화. 첫 번째 측정과 이후 4회 중앙값을 별도로 표시한다. OS·Obsidian 파일 캐시는 비우지 않았다. 따라서 첫 번째 측정은 머신/앱 전체의 완전한 콜드 시작을 뜻하지 않는다.
- 실제 Obsidian에서 격리 측정 플러그인이 제품의 화면/버튼·저장·편집 경로를 호출한다. `performance.now()`부터 해당 비동기 작업/Markdown 완료와 두 번의 animation frame까지의 경과 시간이다. 앱 밖의 브라우저 모사 결과가 아니다.
- 스크롤 값은 목록 최하단으로 `scrollTop` 이동 후 두 프레임까지이다. 지속 스크롤 FPS나 물리적 입력 지연 수치로 해석하지 않는다. 별도로 실제 앱에서 목록·검색·스크롤·편집 복귀를 조작해 확인했다.
- 긴 질문 검색은 `긴 질문`, 연속 입력은 `문→문제→문제 0→문제 00→문제 000`을 한 작업에서 순차 입력한다. 필터는 과목01, 정렬은 문제명. 시작은 전체 대상, 전환은 다음 문제 버튼, 평가는 정답 표시 뒤 3번 버튼으로 실행한다.
- 편집은 동일한 긴 질문(00000)을 정상 관리형 편집 경로로 수정/복원한다. 세션/목록 각각 측정하며 이후 파일을 원본으로 되돌린다. 설정 측정은 Obsidian의 실제 MIA 설정 탭을 연다.
- 측정 장치 초기 입력 스키마/이어하기 초기화 오류가 난 실행과 검증 보조 코드 오류는 유효 표본에서 제외했다. before.json/after.json은 각각 240개 완결 표본만 포함한다.

## 확인된 병목과 변경

1. 목록의 한 페이지에서 최대 300개 질문 Markdown을 만들던 작업을 50개로 제한했다. 전체 검색·필터·정렬·학습 대상은 그대로이며 페이지 버튼으로 나머지를 탐색한다. 긴 질문 결과의 큰 렌더링 비용이 줄었다. 더 많은 페이지 이동이 필요한 사용성 교환이 있다.
2. 검색/필터/정렬/페이지 변경 때 완료된 렌더 Promise 참조가 계속 쌓였다. 10,000문제에서 30회 검색 후 600→18,600개였다. 결과 전용 Component의 이전 자원을 unload/remove하고 현재 결과의 렌더 참조만 유지하도록 바꿨다. 수정 후 100→100개, 현재 결과 Component 1개로 일정하다. 전체 화면 종료 시 마지막 결과도 부모와 함께 unload한다.
3. 새 캐시·입력 지연·저장 배치·알고리즘 변경은 추가하지 않았다. 변경은 `src/ui/study-view.ts`의 목록 페이지/Markdown 자원 수명에 한정했다. FSRS/학습 정책/저장 직렬화/충돌 감지/미완료 사본/복구 코드는 변경하지 않았다.

10,000문제의 이후 4회 중앙값에서 목록 열기 230.9→130.3ms, 긴 질문 검색 900.2→238.5ms, 5회 연속 검색 663.5→439.6ms, 편집 후 목록 갱신 1,072.1→704.4ms다. 저장/활성화 등 직접 수정하지 않은 경로의 차이를 이번 최적화 효과로 주장하지 않는다.

## 저장·파일 접근 조사와 남은 비용

- QuestionIndex는 시작 시 설정된 문제은행/키워드/파생 노트를 읽고 스냅샷을 캐시한다. 일반적인 검색/필터/정렬은 이미 파싱된 인덱스를 사용한다. 편집과 외부 변경/폴더 설정 변경의 캐시 갱신도 실제 앱에서 확인했다.
- 각 반복의 활성화 cachedRead 수, adapter 읽기 수, 전체 파일 접근 및 저장 수는 원시 JSON의 traces에 기록했다. 첫 반복은 과목별 파생 노트를 생성해 후속 반복보다 쓰기/읽기가 많다. 이 차이는 측정값과 함께 보존했다.
- 평가 측정 구간의 adapter 쓰기는 30회 중 24회에서 2회, 6회에서 3회였다. 이 카운터는 이어하기 등 같은 구간의 쓰기도 포함하므로 순수 평가 데이터 파일 저장 횟수로 해석하지 않는다. 약 23MB/96,000회 이력 데이터의 보호된 읽기·병합·직렬화·저장·검증 경로 비용이 남는다. 10,000문제에서 수정 후 평가→UI 응답 중앙값 약 758ms, 첫 화면 약 1.41초, 편집→목록 약 704ms라 즉각적이라고 보기는 어렵다.
- 보호 절차를 건너뛰거나 저장 횟수를 줄이는 변경은 적용하지 않았다. 데이터 보호를 유지하면서 저장 구조를 바꾸려면 별도의 영속 데이터 계약 검증이 필요하다. 현 작업은 목록 병목에 한정한다.
- 정렬/필터/통계·설정의 작은 차이와 스크롤의 약 한 프레임 차이는 측정 변동/프레임 위상 영향을 받을 수 있다. 전 동작이 빨라졌다고 주장하지 않는다.

## 반복 사용과 메모리

수정 전후 각각 검색 30회, 화면 열기·학습·닫기 15회, 활성화·비활성화 5회를 수행했다. 활성 상태에서 인덱스 구독 1개/저장소 구독 2개/화면 1개로 일정했다. 닫으면 인덱스 구독 0개, 비활성화하면 인덱스 이벤트 0개/갱신 타이머 0개로 돌아왔다.

추가로 전후 각각 20회 같은 화면·학습·종료를 반복하면서 전역 이벤트·타이머를 추적하고 가비지 수집 전후 heap 및 닫힌 view의 WeakRef를 확인했다. 이 검사는 시간 측정과 분리했고, QA 프로세스에서만 GC 노출을 잠시 켠 뒤 복원했다. 상세 결과는 `results/resources.json`을 참조한다.

| 빌드 | 수집 후 시작 heap | 20회 후 heap | 닫힌 view 잔존 | 종료 후 전역 이벤트/타이머/화면 |
|---|---:|---:|---:|---|
| before | 94.38 MiB | 95.27 MiB | 0 | 0 / 0 / 0 |
| after | 138.44 MiB | 139.31 MiB | 0 | 0 / 0 / 0 |

수집 전 heap 증가만으로 누수라고 판단하지 않았다. GC 뒤 대체로 안정되고 닫힌 view가 수거됐으므로, 이 반복에서 지속적인 화면/전역 자원 누수는 관측하지 못했다. 확인해 수정한 것은 검색 중 유지되던 렌더 작업 참조 누적이다. heap 수치의 전후 절대값 차이를 메모리 개선율로 사용하지 않는다.

## 기능·보존 검증

- 관련 테스트: 9파일 294개 통과. 목록의 모든 페이지·마지막 항목 검색·전체 결과 학습 선택·IME 중간 입력·느린 이전 Markdown 완료·반복 렌더 자원 해제·편집 복귀 및 기존 저장/복구 테스트를 포함한다.
- 타입 검사·제품 빌드: `npm run build` 통과. `git diff --check` 통과. 새 측정 코드/문제 ID가 제품 번들에 포함되지 않았는지도 검사했다.
- 실제 Obsidian 검증: 15개 통과. 10,000개 첫/다음/마지막 페이지 순서, 마지막 문제 검색, 전체 10,000개 선택, 외부 파일 수정, sourceRoots 1,000↔10,000 전환, 숨겨진 세션 문제 ID 편집과 취소 복귀, 20회 자원 정리를 확인했다.
- 실제 디스크와 메모리 리뷰가 일치하며 96,000개 기존 평가 이력 + 의도한 새 평가 1개만 남고 미완료 저장이 없었다. 외부 수정과 편집은 원본으로 복원했다.
- 프로젝트 node_modules에는 선언된 jsdom이 빠져 있었다. 외부 설치나 의존성 변경 없이 기존 `../simple-study-flow-qa-2026-10-27/test-runtime/node_modules`를 NODE_PATH로 지정해 UI 테스트를 실행했다.
- 전체 테스트: 1,252개 중 1,249개 통과, 2개 건너뜀, 기존 실패 1개. `owned-merge.test.js`의 incoming retention=.8 활성값 강제 기대는 최신 settings lineage/충돌 보존 동작(.8 사본 보존, 활성 .9)과 불일치한다. 수정 전 HEAD를 별도 소스 스냅샷에서 실행해 동일 실패를 재현했다(10개 중 9통과/1실패). 제품 저장 로직이나 그 테스트의 기대값을 이번 성능 작업에서 바꾸지 않았다. 따라서 전체 테스트 완전 통과라고 보고하지 않는다.

## 범위와 한계

실제 모바일 기기에서는 측정하지 않았다. 모바일 성능 검증 결과가 아니며, 데스크톱 결과를 모바일로 일반화하지 않는다. 각 규모는 50개 문제은행으로 고정했으므로 문제마다 파일 하나인 10,000파일 구성·수백만 회 학습 이력·다른 플러그인/테마의 영향은 검증 범위 밖이다. 네트워크/동기화 서비스 지연도 이 로컬 격리 보관함 측정에 포함되지 않는다.

## 재현·근거

- `../performance-qa-2026-10-27/create-fixtures.mjs`: 실제 제품 formatter/FSRS로 합성 데이터 생성. 기존 QA 보관함을 덮어쓰지 않도록 생성 시 거부한다.
- `../performance-qa-2026-10-27/companion.js`: 격리 보관함 이름 검사 후 측정. `plan.json`의 run/label/trials로 실행, results/before.json·after.json에 원시값 기록.
- `../performance-qa-2026-10-27/validation.js`, `resources.js`: 실제 앱 기능·자원 검증. 이 파일들은 제품 저장소/번들에 포함하지 않는다.
- 원시 결과: `../performance-qa-2026-10-27/MIA-Performance-QA/results/`. 유효 완료 파일은 before.json, after.json, native-validation.json + DONE, resources.json + DONE. ERROR 파일은 측정/검증 장치 개발 중 실패 기록이며 완료 표본에는 합치지 않았다.
- 빌드/테스트 로그와 수정 전 재현 소스는 QA 폴더에 보존했다. 원격 푸시·게시·배포 패키지는 생성하지 않았다.
